# Test layout and examples

Every test must protect meaningful public behavior or a consequential failure.
The layouts below are illustrative. Inspect the target manifests, package exports,
and test discovery before choosing paths or commands.

## Python

Example source and test structure:

```text
pyproject.toml
src/product/
  <area>/
    __init__.py              # Explicit public exports
    _implementation.py
tests/
  <area>/
    conftest.py              # Scoped fixtures, doubles, mock setup
    test_<behavior>.py
packages/<package>/
  src/product_<package>/
    __init__.py
    py.typed
  tests/
    conftest.py              # Add only when fixtures are needed
    test_<behavior>.py
```

A root distribution may package multiple source trees, while independent
workspace members may each own a manifest. Preserve the actual packaging model
and test discovery configuration. Do not create another manifest just for tests.

Use `test_<what>_<condition>_<expected_result>` names. A typed fixture follows
the source convention:

```python
# conftest.py
import pytest

from product.storage import MemoryStore


@pytest.fixture(name="store")
def fixture_store() -> MemoryStore:
    return MemoryStore()
```

`product.storage.MemoryStore` above is an illustrative public API, not a bundled
dependency. Use the target's real local implementation or the smallest boundary
double. For resources, use a yielding fixture with reliable teardown. Keep a
fixture's scope as narrow as the sharing and isolation requirements allow;
avoid global autouse setup without a concrete need.

A useful storage scenario invokes public operations and verifies canonical
paths, persisted data, and denied writes. A boundary double can simulate short
reads or failed writes without an external service. Merely checking that a tool
object was constructed provides weaker evidence.

Use pytest fixture injection instead of runtime imports from `conftest.py`.
Run focused tests with the repository's runner, then the required format, lint,
typing, and test gates. Confirm commands in manifests and automation first.

## TypeScript

Example package structure:

```text
packages/protocol-client/
  package.json
  tsconfig.json             # Strict checking of src and tests
  tsconfig.build.json       # src -> dist; excludes tests
  src/
    index.ts                # Explicit public exports
    <implementation>.ts
  tests/
    <behavior>.test.ts
    <boundary>-helpers.ts
```

Follow the actual package's module mode, exports, and runner. For a published
package, check source and tests strictly but build only runtime source and type
declarations. Do not ship test helpers merely to make them importable.

A useful protocol scenario feeds representative events from a fake child process
through the public session API and verifies results and callbacks. Falsy values,
nested structures, or large Unicode payloads earn separate cases only when they
protect distinct data-fidelity risks. Use the package's public entry point;
expected values must not be generated by the decoder under test.

Run the existing package test script, required repository checks, and the build
when packaging is affected. Do not assume a particular runtime or Make target.

## Go

Example package structure:

```text
go.mod
internal/invoice/
  service.go                # Public Service interface and New constructor
  get.go                    # (*service).Get
  get_test.go               # TestGet, package invoice_test
  list.go
  list_test.go
  mocks.go                  # Generated; never edited by hand
  store/
    store.go                # Store interface owned by this package
    mocks.go                # Generated MockStore, in package store
    e2e/
      e2e_test.go           # Suite setup: one real database for the package
      list_test.go          # TestList against the real database
test/
  fixtures/                 # Shared generators and seed helpers
```

Mirror source files: `get.go` is tested in `get_test.go` by `TestGet`. Use the
external test package (`package invoice_test`) so a test can only reach what
callers can reach. An `export_test.go` that re-exports internals widens the
contract for tests and is the Go form of testing private helpers.

One `TestMethod` per public method holds every case as subtests grouped by
concern. Construct the service, its doubles, and the context once at the top:

```go
package invoice_test

func TestGet(t *testing.T) {
    invoiceStore := store.NewMockStore(t)
    svc := invoice.New(invoice.Config{Store: invoiceStore})
    ctx := context.Background()
    invoiceId := uuid.New()

    t.Run("Validation", func(t *testing.T) {
        t.Run("MissingId", func(t *testing.T) {
            got, err := svc.Get(ctx, uuid.Nil)
            assert.Nil(t, got)
            assert.ErrorIs(t, err, invoice.ErrInvalidId)
        })
    })

    t.Run("Success", func(t *testing.T) {
        t.Run("Structure", func(t *testing.T) {
            row := &store.Invoice{Id: invoiceId, SubtotalCents: 1005, TaxRate: 0.10}
            invoiceStore.EXPECT().Get(ctx, invoiceId).Return(row, nil).Once()

            got, err := svc.Get(ctx, invoiceId)
            require.NoError(t, err)

            // Expected values are written by hand, not derived from the converter.
            want := &invoice.Invoice{Id: invoiceId, SubtotalCents: 1005, TotalCents: 1106}
            assert.Equal(t, want, got)
        })
    })

    t.Run("Errors", func(t *testing.T) {
        t.Run("NotFound", func(t *testing.T) {
            invoiceStore.EXPECT().Get(ctx, invoiceId).Return(nil, store.ErrNotFound).Once()

            got, err := svc.Get(ctx, invoiceId)
            assert.Nil(t, got)
            assert.ErrorIs(t, err, invoice.ErrNotFound)
        })
    })
}
```

Conventions that keep these tests honest:

- **Assertions:** use the repository's library, typically `testify` (`assert`
  for checks, `require` when the test cannot continue) or the standard library
  with `go-cmp`. Compare the whole expected struct rather than chosen fields, so
  a new field that is not mapped fails the test.
- **Doubles:** generate mocks for interfaces owned by the consuming package with
  the repository's generator (for example mockery) and regenerate through its
  build target. Pass the real `ctx` and fully built argument structs to
  expectations instead of `mock.Anything` or `mock.MatchedBy`, and state the call
  count (`.Once()`, `.Times(n)`). A mock must return what the real dependency
  returns, including typed sentinel errors.
- **Test data:** random generators (for example gofakeit) suit data the code
  passes through unchanged. For conversion or mapping, write explicit inputs and
  a hand-built expected value; generating both sides with the code under test is
  tautological.
- **Tables:** use a table of cases when inputs form equivalence classes or
  boundaries, with a descriptive `name` per row passed to `t.Run`.
- **Errors:** test the errors the contract maps, such as a sentinel that becomes
  `NotFound`, with `errors.Is` or `assert.ErrorIs`. Do not add a case that only
  shows an arbitrary dependency error propagates.
- **Concurrency:** run with `-race`. Use `t.Cleanup` for teardown, `t.Context()`
  where the Go version provides it, and `t.Parallel()` only when cases share no
  state. Assert on goroutine settlement and cancellation through the public API.

Database and other real-boundary tests live in an `e2e` (or the repository's
equivalent) package beside the component, against a real instance started once
per suite, for example in a container. Seed data through shared fixture helpers,
never through the method under test. Insert a non-matching row so a passing
filter proves exclusion, read server-generated fields back from the database,
and truncate timestamps to the database's precision so round trips compare
equal.

Run focused packages with the repository's target, or directly:

```bash
TZ=UTC go test -race -count=1 ./internal/invoice/...
TZ=UTC go test -race -count=1 ./internal/invoice -run 'TestGet/Errors'
```

`-count=1` disables the test cache; `TZ=UTC` removes host time zone effects.
Follow the repository's own test target when it adds flags or a test runner.

## Test admission examples

| Proposed test | Decision |
| --- | --- |
| A constructor stores each argument in a field | Omit unless this is a meaningful documented behavior with real regression risk |
| A denied public write leaves persisted data unchanged | Keep: protects authorization and data integrity |
| Every private parsing helper returns its current result | Omit: cover the parser through the public decode interface |
| Unknown protocol versions fail with a documented error | Keep: protects interoperability and a supported failure contract |
| A public run settles once after competing cancellation/completion events | Keep when this lifecycle is supported: protects termination and caller state |
| Copy the implementation's transformation to compute expected output | Replace with independently specified examples or invariants |
| Add one test per enum member only to raise coverage | Omit; use one meaningful vocabulary/consumer parity check if drift is a real risk |

Public does not mean every public function needs its own test. Choose cases by
behavior and consequence. Keep essential failure and invariant coverage even
when it requires several assertions or a longer scenario.
