# Word list: M–Z
Source: https://developers.google.com/style/word-list (content adapted under CC BY 4.0). Numbers, symbols, and A–L are in word-list-a-l.md.

## M

- **male adapter**: Don't use. Use a genderless word like _plug_.
- **man hours, manhours, man-hours**: Avoid gendered terms. Use terms like _person hours_.
- **man-in-the-middle (MITM)**: Avoid gendered terms. Use _on-path attacker_ or _person-in-the-middle (PITM)_.
- **managed instance group (MIG)**: OK to abbreviate to _MIG_ on subsequent mention. See also _instance group_.
- **manmade, man made**: Avoid gendered terms. Use a word like _artificial_, _manufactured_, or _synthetic_.
- **manned**: Avoid gendered terms. Use _staffed_ or _crewed_.
- **manpower, man power, man-power**: Avoid gendered terms. Use _staff_ or _workforce_.
- **Markdown**: Always capitalized, even when referring to a nonstandard version.
- **master**: Use with caution. Never use in conjunction with _slave_. Where possible, replace with a specific, accurate term such as _primary_, _main_, _original_, _parent_, _initiator_, _driver_, _controller_, _manager_, _mixer_, _aggregator_, _publisher_, _leader_, or _active_. If the command or code you're documenting uses the literal word _master_, use it only in direct reference to the code item (formatted as code, see https://developers.google.com/style/code-in-text), make clear what you're referring to, and use the new term thereafter. See also _slave_.
- **Material Design**: Capitalize each word.
- **matrix**: Use the plural _matrixes_ unless there is a domain-specific reason (for example, a mathematical context) to use _matrices_.
- **may**: In general, reserve for official policy or legal considerations. To convey possibility, use _can_ or _might_. To convey permission, use _can_. See also _can_, _could_, _might_, _must_, _should_, and _would_. For clarifying who performs an action, see https://developers.google.com/style/voice.
- **MBps**: Short for _megabytes per second_. By convention, don't use _MB/s_. See https://developers.google.com/style/units-of-measure.
- **Mbps**: Short for _megabits per second_. By convention, don't use _Mb/s_. See https://developers.google.com/style/units-of-measure.
- **media type**: In general, use _media type_ (https://www.iana.org/assignments/media-types/media-types.xhtml). Where you need to refer to a _content type_ (for example, when you mention the `Content-Type` HTTP header), it's OK to use _content type_ to avoid confusion. Don't use _MIME type_.
- **meta\***: See guidance about hyphens with prefixes at https://developers.google.com/style/hyphens#prefixes.
- **metafeed**: Not _meta-feed_.
- **metageneration**: Not _meta-generation_.
- **method**: In programming contexts where _method_ refers to a member of a class (as in Java), avoid also using the word generically to mean "approach" or "manner."
- **metropolitan area (metro)**: In networking, a _metro_ is a city where a colocation facility is located.
- **microservices**: Not _Microservices_ or _micro-services_.
- **might**: Use to convey possibility or an uncertain outcome (for example, "You might be prompted to enter your credentials"). See also _can_, _could_, _may_, _must_, _should_, and _would_. For clarifying who performs an action, see https://developers.google.com/style/voice.
- **MIME type**: _MIME_ stands for "Multipurpose Internet Mail Extensions" and originally referred to email standards. Don't use _MIME_ when you mean _media type_ (https://www.iana.org/assignments/media-types/media-types.xhtml). If that might be ambiguous to an audience familiar with _MIME_, you can write _media (MIME) type_ for clarity.
- **mobile**: Don't use as a standalone noun. Specify _mobile phone_, or if you're talking about more than phones, use _mobile device_.
- **mobile data**: Use instead of _cellular data_.
- **mobile device**: Use when referring to more than phones (for example, tablets and phones). OK to use _phone_ (without _mobile_) when the context is clear.
- **mobile network**: Use instead of _cellular network_.
- **mobile phone**: If you're talking about more than phones, use _mobile device_. OK to use _phone_ (without _mobile_) when the context is clear.
- **mom test**: Don't use _mom test_, _grandmother test_, _grandma test_, or _girlfriend test_. Use terms like _beginner user test_ or _novice user test_.
- **monkey, monkey test**: Don't use _monkey_ to refer to people. When referring to tests, refer to the specific function, for example _automated, random tests_.
- **multi\***: See guidance about hyphens with prefixes at https://developers.google.com/style/hyphens#prefixes.
- **multi-cluster**: Hyphenate. Prefixed words are generally closed, but this is an exception because it's an established term.
- **multi-region, multi-regional**: Hyphenate when referring to a Google Cloud location that consists of more than one region. You can use _multi-regional_ as an adjective in the context of multi-regions, but consider _multi-region_ as an attributive noun instead, as in "The dataset is in the EU multi-region location." Use _multiregional_ in other contexts.
- **multi-service**: Hyphenate. Prefixed words are generally closed, but this is an exception because it's an established term.
- **multi-tenancy**: Hyphenate. Prefixed words are generally closed, but this is an exception because it's an established term.
- **must**: Use to describe a required action or state (for example, "You must have the Editor role"). You can also write _you need_ to convey a requirement. See also _can_, _could_, _may_, _might_, _should_, and _would_. For clarifying who performs an action, see https://developers.google.com/style/voice.

## N

- **N/A**: Not _NA_. Spell out as _not available_ or _not applicable_ on first reference.
- **name server**: Not _nameserver_.
- **namespace**: Not _name space_.
- **native**: Avoid using _native_ to refer to people. For software products, use a more precise term, for example _built-in_ for a feature that's part of a product. _Native_ isn't necessarily clear: _cloud-native_ could mean written for the cloud, built in to a cloud platform, or currently existing in a cloud platform. Alternatives to _cloud-native_ include _modern cloud_, _born in the cloud_, _cloud first_, and _cloud-born_.
- **navigation bar**: Don't use to refer to a _navigation menu_. See https://developers.google.com/style/ui-elements#term-navigation-menu.
- **neither**: Write _neither A nor B_, not _neither A or B_.
- **network IP address**: Don't use. Use _internal IP address_.
- **new, newer**: Avoid in timeless documentation because the word can become outdated. _New_ also implies the reader knows the older product. If you must use _new_, give a reference point such as a version number or release date. Don't use _newer_ for a specific version of a product; use _later_, with a version number or release date. In Android documentation, use _higher_ instead of _later_. Recommended: The service's network analysis feature reports on network health. Not recommended: Network analysis, a new feature in the service, reports on network health. See https://developers.google.com/style/timeless-documentation.
- **ninja**: Don't use to refer to a person. Use a term such as _expert_. OK in reference to companies, tools, software packages, and other entities that use the term in their names.
- **non\***: See guidance about hyphens with prefixes at https://developers.google.com/style/hyphens#prefixes.
- **nonce**: Use with caution: the term has a secondary slang meaning that can confuse global readers. Always define on first use, and use only in specific technical contexts such as authentication and blockchain. In end-user documentation and other contexts, use a descriptive phrase such as _a number that will be used only once_.
- **non-key**: An exception to the usual preference for closed forms.
- **NoOps**: Don't use. Use _fully managed_. If you must include the term, define it at first use with language such as _fully managed_ or _no operations_, but not _non-operational_. Don't use _noops_. For an instruction that does nothing, use _no-op_ (https://wikipedia.org/wiki/NOP_(code)) or the specific instruction name for your context.
- **NoSQL**: Not _No-SQL_ or _No SQL_.
- **notification drawer**: In Android contexts, don't hyphenate. Lowercase except at the beginning of a sentence, heading, or list item.
- **now**: Avoid when describing features of products or services because the word is implied. If the intent is a comparison between past and present, you can use _now_, for example, "In versions of the tool earlier than 1.10, you could use only the default value, but now you can assign a custom value." Recommended: This feature lets you use combinations of user properties. Not recommended: This feature now lets you use combinations of user properties. See https://developers.google.com/style/timeless-documentation.
- **nuke**: Don't use. Use _remove_ or _attack_. For example, a _denial-of-service attack_.

## O

- **OAuth 2.0**: Not _OAuth 2_, _OAuth2_, or _Oauth_.
- **off-the-shelf, commercial off-the-shelf (COTS)**: Use more widely understood terms like _ready-made_, _prebuilt_, _standard_, or _default_.
- **old, older**: Don't use to refer to a previous version of a product. Use _earlier_, and provide a version number by which to understand it. In Android documentation, use _lower_ instead of _earlier_. Recommended: This functionality doesn't work in versions earlier than 1.17.0. Not recommended: This functionality doesn't work in older versions. See https://developers.google.com/style/timeless-documentation.
- **omnibox**: Don't use. Use _address bar_.
- **once**: If you mean _after_, use _after_ instead of _once_.
- **on-premises**: Not _on prem_, _on premise_, or _on-premise_. Hyphenate as any part of speech. Use for a customer's resources that they manage in their own facilities. Don't use _peer_. OK as a noun when repeating a full phrase like _an on-premises environment_ would be awkward, but prefer the complete phrase. Recommended: An on-premises database. Recommended: The database runs on-premises. OK: Moving data from on-premises to Google Cloud.
- **OS**: OK to use as a shortening of "operating system."
- **outpost**: Don't use. Use _channel_. Recommended: social media channels.
- **outside the box, out of the box, out-of-the-box**: Avoid in a figurative way. OK to use literally.
- **overview screen**: In Android documentation, don't use. Use _recents screen_.

## P

- **PaaS**: Write out on first mention: _platform as a service (PaaS)_.
- **page**: Use to refer to a whole web page (which can include text, images, links, banners, navigational panes, and other features), or to a sub-page of a _console_ in particular. See also _documentation or document or documents_. Recommended: To refresh the page, press F5.
- **parameter**: In API documentation, _parameter_ is usually short for _query parameter_: a `NAME=VALUE` pair appended to a URL in an HTTP `GET` request. In some contexts the term can have other meanings.
- **parent-child or parent/child**: Not _parent – child_ or _parent—child_.
- **path**: Avoid _filepath_, _file path_, _pathname_, or _path name_ if possible.
- **peer gateway**: Don't use _on-premises gateway_ when you mean a _peer gateway_. A peer gateway can be an on-premises device or service or another cloud gateway.
- **peer network**: Don't use _on-premises network_ when you mean a _peer network_. A peer network can be an on-premises network or another cloud network.
- **peering zone**: Not _peer zone_.
- **per**: To express a rate, use _per_ instead of the division slash (/), unless space constraints require the slash (see https://developers.google.com/style/units-of-measure#rates). Avoid _per_ in contexts other than rate units. Recommended: requests per day; create a policy for each Pod; according to the style guide; in response to your request. Not recommended: requests/day; create a policy per Pod; per the style guide; as per your request.
- **performant**: Avoid where possible. Use a more precise term. Recommended: an accurate machine learning model. Not recommended: a performant machine learning model.
- **persist**: Don't use as a transitive verb. Best to avoid as a verb at all, especially in passive voice (https://developers.google.com/style/voice). Recommended: To make the token persistent ... OK: To make the token persist ... Not recommended: The token is persisted ... Not recommended: To persist the token ...
- **persistent disk**: Not _PD_. Lowercase except at the start of a sentence.
- **personally identifiable information (PII)**: Some government agencies use the less common _personally identifying information_; use that alternate term only when referring to a document that uses it.
- **pets versus cattle, pets vs. cattle, pets v. cattle**: Don't use. Use more precise terms like _persistent versus dynamic_ or _manually configured versus automated_. See https://developers.google.com/style/inclusive-documentation#figurative-language.
- **plain text**: In most contexts, use _plain text_, but use _plaintext_ in a cryptography context.
- **please**: Don't use in the normal course of explaining how to use a product, even for a difficult task. Don't use the phrase _please note_. Use _please_ only when asking for permission or forgiveness, for example, when what you're asking benefits you, inconveniences a reader, or suggests a potential issue with a product. Recommended: If the issue persists, please contact your account representative. See https://developers.google.com/style/tone#politeness.
- **plugin (noun), plug-in (adjective), plug in (verb)**: Use the noun _plugin_ for the software component. Use the adjective _plug-in_ when referring to the action of installing a software component. Use the verb _plug in_ when describing the process of installing a software component.
- **PM**: See _AM, PM_.
- **point to**: Use for the action of pointing the mouse pointer (focus). Doesn't imply a length of time waiting for the UI to react. Similar to _hold the pointer over (hover)_; in most cases, prefer _hold the pointer over_ if you want the user to wait for the UI to react.
- **POJO**: If you're not actually writing about a Plain Old Java Object for a Java audience, use _simple object_. You can write _a simple object, similar to a POJO in Java_ if that helps your audience.
- **PoP**: Acronym for _point of presence_. Recommended: point of presence (PoP). Not recommended: point of presence (POP).
- **pop-up, popup**: Don't use. For a window that appears and asks for, or presents, additional information, use _dialog_. For a menu that rises from an interface (such as a right-click context menu), use _menu_.
- **populate**: OK for a process populating a table or other entity. For a person, use _fill in_. Recommended: The SQL command populates the table with sample data. Recommended: When you have finished filling in the form ... Not recommended: When you have finished populating the form ...
- **port**: Use _listen on_ (not _to_).
- **portal**: Don't use to refer to the Google Cloud console. See _console_.
- **possible**: Don't use _possible_ or _impossible_ to mean _you can_ or _you can't_.
- **PostgreSQL**: If the UI uses the name _Postgres_, it's OK to match the UI. Don't use _PostgreSQL_.
- **postmortem**: Avoid in general usage. Use _retrospective_. In disaster recovery (DR) and DevOps contexts, use _blameless postmortem_.
- **practitioner**: Avoid using without supporting information that defines the roles you're referring to. Recommended: The framework describes best practices for architects, developers, administrators, and other cloud practitioners. Not recommended: The framework describes best practices for cloud practitioners.
- **pre\***: See guidance about hyphens with prefixes at https://developers.google.com/style/hyphens#prefixes.
- **prebuilt**: Not _pre-built_.
- **precapture**: Not _pre-capture_.
- **preemptible**: Not _pre-emptible_ or _pre-emptive_.
- **pre-existing**: Not _preexisting_.
- **preferred pronouns**: Don't use. Use _pronouns_.
- **prerecorded**: Not _pre-recorded_.
- **pre-shared key**: Not _preshared key_.
- **presently, at present**: Avoid because the word or phrase is implied. It can also prematurely disclose product or feature strategy or inappropriately imply that a product or feature might change. See also _as of this writing_ and _currently_. Recommended: This setting is required. Not recommended: At present, this setting is required. See https://developers.google.com/style/timeless-documentation.
- **press**: Use for pressing a key or key combination to cause an action, and for mechanical buttons. For on-screen and soft (capacitive) buttons, use _tap_. Recommended: Press Control+C (or Command+C on macOS).
- **presubmit**: Not _pre-submit_.
- **primitive**: Use with caution. Don't use in a disparaging sense.
- **project**: In Google Cloud documentation, use _Google Cloud project_ on first mention and in any context where there might be ambiguity about what kind of project you mean.
- **pros**: Don't use. Use a more precise term, such as _advantages_.

## Q

- **quick, quickly**: What might be quick for you might not be quick for others. Try eliminating the word; usually the same meaning can be conveyed without it.
- **quota**: In API contexts, often refers to API usage limits. Where possible, use a more specific term such as _usage limit_; _quota_ means many different things to many different people. In some contexts, such as Google Cloud documentation, _quota_ is the standard term, so use it.

## R

- **RDP**: Don't use as a verb. Use _connect using RDP_. If it's clear from context that RDP is being used, it's OK to use _connect_.
- **re\***: See guidance about hyphens with prefixes at https://developers.google.com/style/hyphens#prefixes.
- **read-only**: Not _read only_. Always hyphenate.
- **recents screen**: In Android contexts, use instead of _overview screen_.
- **redline**: Don't use as a verb. Use precise terms appropriate to the context. For editing or reviewing, refer to those actions or to _tracking changes_. For setting priorities and planning work, refer to those actions or to _priority lining_.
- **regex**: Don't use. Use _regular expression_.
- **rehost**: Use for migrating an app or workload with no or minimal changes. Also known as _lift and shift_ (see https://cloud.google.com/architecture/migration-to-gcp-getting-started#rehost_lift_and_shift). On first mention, associate rehost with lift and shift; OK to use _rehosting_ after first mention. Recommended: You can use this reference architecture to efficiently rehost (lift and shift) on-premises applications to the cloud. Recommended: The first step to modernization is to rehost your application in the cloud (also known as lift and shift). Don't use _the forklift approach_.
- **repo**: Don't use. Use _repository_.
- **Representational State Transfer**: Don't use. To people unfamiliar with REST, the expansion is meaningless; refer to it as REST without explaining what it stands for.
- **reservation, off the**: Don't use.
- **resource record set**: Not _resource recordset_.
- **retarded**: Don't use. For a system or component being slowed, use _slowed_.
- **retriable, triable**: Don't use unless a code item uses that spelling. Outside of code font, write around the term.
- **retryable, tryable**: Where possible, write around these. For example, write _you can try it again_ or _can be tried again_.
- **review**: If you mean "read, potentially for the first time," use _read_. If you mean "read critically, commenting on problems" (as in _code review_), _review_ is fine. Avoid phrasing like "If you've never heard of OAuth, then review the OAuth documentation."
- **RFC**: When referencing an RFC specification, use a space between _RFC_ and the number (for example, _RFC 2318_).
- **roll out**: Don't use to mean a sudden or instantaneous launch. If you use _roll out_, define what you mean. When possible, use a more precise, non-figurative term like _gradual_, _in stages_, _phases_, or _progressive_.
- **RTFM**: Don't use. Use a more precise phrase like "For more information, see ...."
- **runbook**: Not _run book_.
- **runtime, run time**: Use the noun _runtime_ for the environment in which software runs, such as a Ruby or Java runtime. Use the noun phrase _run time_ for the time during program execution when something occurs, as contrasted with _compile time_. Recommended: The profiler collects data at run time, and the scheduler uses this data at compile time to improve performance for subsequent runs. Recommended: The App Engine standard environment has two generations of runtime environments. The second-generation runtimes significantly improve the capabilities of App Engine.

## S

- **SaaS**: Write out on first mention: _software as a service (SaaS)_.
- **sane**: Don't use. Use a word like _valid_ or _sensible_.
- **sanity check**: Don't use. Use a term like _quick check_, _confidence check_, _preliminary check_, or _coherence check_.
- **SAP**: Pronounced as the individual letters _S_, _A_, _P_, so write _an SAP system_, not _a SAP system_. See https://developers.google.com/style/abbreviations#articles.
- **scale**: Don't use _scale_ alone to say that something is large or increasing. Include supporting words for magnitude or direction: scaling up or down (for example, changing a machine type to add or remove CPUs or RAM) or scaling out or in (adding or removing instances from a group). Recommended: The system performs better at a larger scale. Not recommended: The system performs better at scale. Recommended: The system scales up quickly, but it scales down more slowly. Not recommended: The system scales quickly.
- **screenshot (noun)**: Not _screen shot_ or _screensnap_. Don't use as a verb; use _take a screenshot_.
- **scroll**: OK as a verb, but if possible use a term that isn't implementation-specific, for example _go to the section_ instead of _scroll to the section_. If you use _scroll_, don't use directional language like _scroll up_. See https://developers.google.com/style/accessibility#document-rendering.
- **Search (as part of product name)**: Capitalize _Search_ when referring to a product like Google Search.
- **Search Console**: Capitalize each word.
- **see**: OK as a general term and when referring to links and cross-references. Research indicates that language relating to sight is OK for a wide range of readers. See https://developers.google.com/style/cross-references.
- **select**: Use for choosing an item from among multiple options, selecting text, or marking a checkbox. Recommended: Select **Automatically check for updates**. Not recommended: Check **Automatically check for updates**.
- **sensitive**: _Sensitive_ data is data whose release might be harmful. See _confidential_.
- **service**: OK to refer to Google products, such as Google Kubernetes Engine or Compute Engine, as _services_. If _services_ leads to ambiguity, use the product names.
- **service level agreement**: Lowercase when referring to service level agreements in general. OK to use title case (_Service Level Agreement_) for a specific document. OK to abbreviate as _SLA_ after first use.
- **service level indicator**: Lowercase except at the beginning of a sentence, heading, or list item. OK to abbreviate as _SLI_ after first use.
- **service level objective**: Lowercase except at the beginning of a sentence, heading, or list item. OK to abbreviate as _SLO_ after first use.
- **setup (noun or adjective), set up (verb)**: One word as a noun or adjective; two words as a verb.
- **sexy**: Don't use. Use precise, positive words such as _fast_, _powerful_, or _elegant_.
- **SHA-1**: Not _SHA1_, except in string literals/enums and in hyphenated phrases such as _HSA-SHA1_.
- **shall**: Avoid except under advice from a lawyer. See _should_.
- **she, her, hers**: Don't use a gendered pronoun except for a specific individual of known gender. Use _they_ and _their_ for the general singular pronoun.
- **sherpa**: If possible, use a more precise term. For example, if you mean _guide_, use that term.
- **shift left**: In general, avoid using to mean moving something earlier in time. Use a less figurative phrase such as _shift earlier_ or _move to an earlier phase_. The term relies on the non-universal assumption that the natural flow is left to right. OK to use _shift left_ and _shift right_ for binary multiplication and division.
- **should, should be**: Generally avoid. _Should_ is ambiguous by definition. For alternatives, see https://developers.google.com/style/prescriptive-documentation#word-choice. See also _can_, _could_, _may_, _might_, _must_, and _would_.
- **sign-in (noun or adjective), sign in (verb)**: Not _log in_ or _signin_.
- **sign into**: Don't use. Use _sign in to_.
- **sign-on, sign on**: Don't use either form on its own. Use the hyphenated version as part of _single sign-on_.
- **sign-out (noun or adjective), sign out (verb)**: Not _log out_ or _signout_.
- **simple, simply**: What might be simple for you might not be simple for others. Try eliminating the word; usually the same meaning can be conveyed without it.
- **since**: If you mean _because_, use _because_. _Since_ is ambiguous; it can refer to the passage of time. _Because_ refers to causation or the reason for something.
- **single most**: Not _singlemost_.
- **single pane of glass**: Avoid. The term favorably compares a centralized control and monitoring interface against several disparate interfaces. It can almost always be replaced by _single interface_ or _unified interface_.
- **single sign-on (noun or adjective)**: Hyphenate _sign-on_ in _single sign-on_.
- **slave**: Don't use. Use alternatives appropriate to your domain, such as _worker_ or _replica_. If replacing _master_ and _slave_ together, consider _primary_/_secondary_, _primary_/_replica_, _original_/_replica_, _controller_/_worker_, _initiator_/_responder_, _mixer_/_leaf_, _aggregator_/_collector_, _publisher_/_subscriber_, _leader_/_follower_, and _active_/_standby_. If the command or code you're documenting uses the literal word _slave_, use it only in direct reference to the code item (formatted as code, see https://developers.google.com/style/code-in-text), make clear what you're referring to, and use the new term thereafter. For example, "Invoke the secondary (`slave`) process directly when debugging issues between the primary and secondary processes." See also _master_.
- **slice and dice**: Don't use. Use specific terms appropriate to the task, such as _segment data for analysis_ or _break information into smaller parts_.
- **smartphone, smart phone**: Don't use. Use _mobile phone_ or _phone_. If you're talking about more than phones, use _mobile device_. OK to use _phone_ (without _mobile_) when the context is clear.
- **soon**: Avoid in timeless documentation because the word can become outdated. It can also prematurely disclose product or feature strategy or inappropriately imply that a product or feature might change. See also _eventually_ and _future_. Recommended: This setting is optional. Not recommended: This setting is optional for existing applications but will soon be required for all applications. See https://developers.google.com/style/timeless-documentation.
- **spin up**: As in _spin up an instance_. Avoid unless referring to a hard disk; use a less colloquial term like _create_ or _start_.
- **SQL**: Refer to _a SQL_ (pronounced "a sequel"), not _an SQL_. See https://developers.google.com/style/abbreviations#articles.
- **ssh and SSH**: Don't use `ssh` or SSH as a verb. SSH is a secure communications protocol; `ssh` is a utility. Recommended: To establish an SSH connection, use the `ssh` command. Recommended: Connect to the instance by using SSH. Not recommended: `ssh` into your remote shell.
- **ssh'ing**: Don't use. See also _ssh and SSH_. Recommended: When you use `ssh` to log in ...
- **startup (noun or adjective), start up (verb)**: One word as a noun or adjective; two words as a verb.
- **static external IP address**: Don't use _static IP address_ or _external IP address_ to refer to static external IP addresses.
- **status bar**: Not _statusbar_ or _status-bar_. Lowercase except at the beginning of a sentence, heading, or list item.
- **STONITH, STOMITH**: Avoid graphic or metaphorical language (https://developers.google.com/style/inclusive-documentation#graphic-language). Explain the relevant feature instead, such as _fence failed nodes_.
- **style sheet**: _Style sheet_ and _stylesheet_ are both acceptable. Be consistent throughout a given document.
- **sub-command**: Not _subcommand_.
- **subnet**: OK as a shortening of _subnetwork_. Use the same term consistently throughout your document. See https://cloud.google.com/compute/docs/vpc/#subnets_vs_subnetworks.
- **subtree**: Not _sub-tree_.
- **subzone**: Not _sub-zone_ or _sub zone_.
- **such as**: Use to introduce examples or draw comparisons. _Such as_, _like_, and _include_ introduce non-exhaustive lists, so it's redundant to combine them with _etc._, _so forth_, or _and more_. See also _etc._ and _like_. See https://developers.google.com/style/format-examples.
- **surface**: Avoid as a transitive verb; use a more specific term such as _make people aware of_ or _expose_. Recommended: To make the audit logs available, you must configure the monitoring system. Not recommended: To surface audit logs, you must configure the monitoring system.

## T

- **tab**: When referring to the sub-pages of a _console_, use _page_ instead of _tab_.
- **table name**: Two words. Set specific table names in code font.
- **tablet**: _Tablet_ is OK. If you don't know whether it's a tablet or a phone, use _device_.
- **tag**: See _element_.
- **tap**: In Android documentation, use for on-screen and soft (capacitive) buttons. Use instead of _click_ when the environment is definitely a touch device. Use instead of _touch_; however, _touch & hold_ (not _touch and hold_) is OK. For mechanical buttons, use _press_.
- **tap & hold, tap and hold**: In Android documentation, don't use. Use _touch & hold_ (not _touch and hold_).
- **tarball**: Don't use. Use _tar file_.
- **target**: Avoid as a verb when possible, especially in reference to people; for some readers it has aggressive connotations. Instead of "targeting" audiences, attract them, appeal to them, or make their lives easier. OK as an adjective, as in _target audience_, but consider rephrasing for clarity with phrases such as _intended for_, _looking for_, _focused on_, and _interacting with_.
- **terminate**: Avoid as a synonym for _stop_. Use words like _stop_, _exit_, _cancel_, or _end_. For a context where _terminate_ can mean _stop_, see https://developers.google.com/style/code-syntax#linux-signals. In contexts such as telephony and networking, _terminate_ has specific technical meanings that aren't synonyms for _stop_; there you can use it.
- **text box, textbox**: Don't use. Use _box_ (see https://developers.google.com/style/ui-elements#term-textbox). In Google Cloud and Google Workspace documentation, use _field_ instead of _box_. For example, "In the **Instance** field, specify a value less than 64 characters long."
- **their (singular)**: See _they_.
- **then**: Although casual usage often omits _then_ in _if...then_ statements, include helper words like _then_ in technical documentation. See https://developers.google.com/style/translation#clear-language.
- **they (singular)**: The preferred gender-neutral pronoun. Whether singular or plural, it always takes the plural verb. Recommended: A user enters their password, and then they insert their security key. See also _gender-neutral he_.
- **third party (noun), third-party (adjective)**: Spell as _third party_ as a noun and _third-party_ as an adjective. Avoid abbreviating to _3rd party_ or _3rd-party_. See https://developers.google.com/style/numbers#ordinal-numbers.
- **this, that**: Where possible, put a noun after _this_ or _that_ for clarity. If that results in clunky prose, don't do it, but still think about what the noun would be. If you aren't sure what noun _this_ or _that_ refers to, consider rephrasing; otherwise your reader probably won't know either.
- **timeframe**: Not _time frame_. Avoid where possible, or use an alternative such as _period_, _schedule_, _deadline_, or _when_. If you do use it, write it as one word.
- **timeout (noun), time out (verb)**: One word as a noun; two words as a verb.
- **timestamp**: Not _time stamp_.
- **time to live**: Not _time-to-live_. Abbreviate as _TTL_ after first use.
- **time zone (noun), time-zone (adjective)**: Spell as _time zone_ as a noun and _time-zone_ as an adjective. See also _wake lock (noun), wake-lock (adjective)_.
- **tl;dr**: Don't use. Use something like _To summarize_, or revise the sentence.
- **toolkit**: Not _tool-kit_ or _tool kit_.
- **touch**: In Android documentation, don't use. Use _tap_. However, _touch & hold_ is OK.
- **"touch & hold"**: Not _touch and hold_.
- **touchscreen**: Not _touch screen_.
- **traditional**: If possible, use a more precise term. Recommended: Conventionally, Python function names are lowercase, with words separated by underscores. Not recommended: Traditionally, Python function names are lowercase, with words separated by underscores. Recommended: This tutorial explains how to migrate from an on-premises data warehouse to BigQuery. Not recommended: This tutorial explains how to migrate from a traditional data warehouse to BigQuery.
- **transpile**: Not _transcompile_.
- **tribal knowledge, tribal wisdom**: Don't use. Use a less figurative term to indicate knowledge held by a group of people.
- **trojan**: Lowercase when referring to malware.
- **turn on**: In procedures, use the appropriate label and action for the UI element the user interacts with (see https://developers.google.com/style/ui-elements). For turning on or activating an option or feature, use _turn on_ or _enable_ consistently throughout your document. Recommended: To turn on Magic Mode, follow these steps. Recommended: In **Settings**, click the **Magic mode** toggle to the on position.
- **tutorial**: OK to use. See _documentation_.
- **type**: In general, use _enter_ instead of _type_ because there is typically more than one way to enter text (such as pasting or speaking).
- **typically**: Use to describe what is usual or expected under normal circumstances. Don't use as the first word in a sentence, as that can leave the meaning open to misinterpretation.
